# 项目脉络维护约定

## 接手与沉淀

1. 按任务名称、症状或报错查首页，必要时搜索 `questions/` 和 `guides/`。核对环境、版本和权威来源，有记录的验证办法优先于重新探索。已知的失败路径也要核对当时的前提。
2. 用户首次主动指定要留存的内容时，先找同一主题。已有条目在原处补充，新主题才建页并登记到首页。一条提 MR 的请求本身只表达本次任务。「把提 MR 的流程记下来」同时选中了长期维护的主题。
3. 选中的主题跨会话持续维护。在工作中拿到新证据、执行结果或用户纠正时，比对受影响的结论。任务结束前更新条目、相关索引和需要留存的变化。同一份材料可以支持多个条目，沿来源路径或旧做法搜索其他引用。仓库已有手册时引用具体章节，只有脉络条目由本约定自动维护。

## 如何判定变化

| 同一主题收到的新信息 | 动作 |
| --- | --- |
| 正式规范已生效，或可核验的配置和结果足以推翻同一环境下的技术结论 | 更新当前做法，注明范围、依据和日期。将旧做法及替换原因移入历史，修正同样受影响的条目。 |
| 存在矛盾，生效范围或证据仍不清楚 | 在条目当前结论附近写明「待核实」、双方依据、受影响的步骤和最小核验办法。保留上次已确认的结论及其适用边界。若边界也存疑，下次执行该步骤前先核验。 |
| 一次临时绕行成功，或两个来源适用的环境、版本不同 | 标明这次观察的前提与结果，分别写清适用范围。把一次执行升级成正式流程，需要对应的规范依据。 |
| 仅增加佐证或修正措辞 | 在原处补充。材料日期较新本身不能证明旧结论失效。 |

发生实质替换或有未决冲突时，在[变更记录](log.md)追加日期、条目、原说法、新证据和处理结果。在本次回复中说明哪些任务受影响、旧做法改成了什么或哪一步仍需核实，并给出依据。后续证据解决冲突时，更新当前条目并追加解决记录。首页继续指向当前条目，历史步骤只用于解释当时的选择。

## 核对来源

在接手已收录主题或吸收新资料时，从项目根目录运行以下命令。

```sh
python3 context/check.py
```

检查器比较标记过的本地来源与上次核对时的 SHA-256，列出受影响的条目。退出码 `0` 表示所跟踪的文件匹配，`1` 表示来源有变或缺失，`2` 表示标记或检查出错。文件变化只提示复查。文件一致时，仍须对照刚收到的材料和实际使用情况。外部链接、用户消息和运行结果由接手者直接核实。

看到提醒时，打开指向的章节和相关规范，判断它影响哪条说法。来源移动时先确认新位置。来源消失又找不到替代依据时，保留待核实提醒。审阅完成后，用 `sha256sum <来源文件>` 取得当前摘要，更新条目相应依据行并重跑检查。可以登记「待核实」后更新已读材料的摘要，但未决事项须保留在条目正文，供下次接手。

## 用于另一个项目

复用本约定、三个子目录的说明、检查器及其测试。在新项目的 `context/README.md` 写下项目目标，从空的主题索引和变更记录开始。在该项目给 AI 的入口说明里链接索引，约定接手时查阅、用户选定新主题时收录、已有主题遇到新依据时更新并提醒。条目内容和来源取自新项目。
